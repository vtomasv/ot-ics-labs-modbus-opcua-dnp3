# Laboratorio 04 — Control DNP3 de señal

**Duración orientativa:** 45 minutos · **Protocolo:** DNP3/TCP · **Modo:** maqueta local, educativa y defensiva.

> **Aislamiento y uso legal obligatorios.** Ejecute esta práctica únicamente en el repositorio, en un equipo de práctica y dentro de la red Docker interna del Compose. No la conecte a una red OT, una RTU, un PLC, un semáforo, un SIS o un activo público/industrial. No publique ni redirija `502/TCP`, `4840/TCP` o `20000/TCP`, no cambie los destinos fijos y no pruebe contra terceros. El material es educativo; cualquier actividad fuera de un entorno autorizado puede ser ilegal y peligrosa.

## 1. Objetivo y resultado esperado

El objetivo es distinguir **técnica representada** de **observación**:

1. ejecutar una orden DNP3/TCP real entre el master nativo de `trainer` y el outstation OpenDNP3 del servicio `dnp3`;
2. verificar la respuesta de control y la lectura de retorno del punto analógico índice 0;
3. correlacionar el valor solicitado `0`, el valor observado `0` y el estado `traffic_signal=0` (rojo virtual) sin confundir la consola con un analizador de paquetes;
4. capturar y examinar TCP/20000 con `tshark`;
5. mapear la conducta de forma acotada a MITRE ATT&CK for ICS **T0831 — Manipulation of Control** y proponer controles conceptuales IEC 62443 FR2, FR3, FR5 y FR6.

El control DNP3 está representado por una transacción de red auténtica dentro de Docker. El efecto de proceso es un cambio en un **gemelo digital**. No hay hardware PLC/RTU, actuador, semáforo físico ni SIS: la escena 3D, el semáforo y sus luces son software.

**Criterio global:** la práctica está lograda cuando el informe demuestra (con al menos dos fuentes independientes) una solicitud DNP3 en TCP/20000, una respuesta válida, el readback DNP3 de índice 0 igual a 0, la vista virtual roja y las limitaciones del escenario. La simple presencia del preámbulo `05 64`, una alerta del panel o un JSON de navegador no es suficiente.

## 2. Prerrequisitos y límites del entorno

- Docker Engine y Docker Compose v2.
- Al menos 2 GB libres para imágenes y evidencias. En ARM64 se necesita emulación `linux/amd64`, porque la dependencia fijada de DNP3 del repositorio no es una pila industrial de producción.
- `tshark` o Wireshark en el anfitrión para leer el PCAP. `tcpdump` se ejecuta dentro del contenedor `plant`.
- Conocer el estado y la topología del repositorio antes de iniciar. No modifique scripts para parametrizar destinos.
- Use solo las acciones existentes `dnp3-signal` y `reset` en esta práctica. No ejecute desde aquí `modbus-write`, `opcua-write` ni `intercept`; esos son escenarios de otros laboratorios.

El navegador solo ve la consola publicada en `127.0.0.1:8080` (o el puerto local explícito de su `.env`). La API principal llama al operador `trainer` por la red Docker `control`; el master de `trainer` abre una conexión al destino fijo `plant:20000`. El servicio `dnp3` usa `network_mode: service:plant`, por lo que el outstation comparte el namespace de red de `plant`. No hay un puerto industrial publicado al anfitrión.

## 3. Topología y modelo de confianza

```text
Navegador del anfitrión
  127.0.0.1:8080  ── HTTP/JSON de consola ──> plant:8000 (API + gemelo)
                                                │
                                                └─ HTTP interno ──> trainer:8100
                                                                      │
                                                                      └─ DNP3/TCP ──> plant:20000
                                                                                       (outstation dnp3)
                                                                                              │
                                                                                              └─ API interna/loopback del gemelo

Suricata comparte el namespace de plant y observa pasivamente la interfaz de control.
```

| Nodo | Rol real en la maqueta | Zona didáctica | Evidencia que produce |
|---|---|---|---|
| `trainer` | Operador y master DNP3 nativo | Red `control` interna | Salida JSON del master y solicitud DNP3 |
| `dnp3` | Outstation OpenDNP3 | Namespace de `plant` | Respuesta de control y readback |
| `plant` | API, proceso y vista de estado | Control/visualización emulados | `/api/state`, eventos, semáforo virtual |
| Navegador | HMI/SCADA de observación local | Host, loopback | Captura de pantalla y solicitudes HTTP a la API |
| `suricata` | Sensor pasivo | Namespace de `plant` | EVE JSON de alertas, si la firma aplica |

La consola **no** es el master DNP3 ni abre `plant:20000` directamente. Una solicitud del navegador a `/api/scenario/dnp3-signal` es una solicitud de aplicación a `plant`; después `plant` invoca al operador interno. Por tanto, no atribuya los bytes HTTP del navegador a un frame DNP3 del PCAP. La red Docker `control` es un conducto de entrenamiento, no una DMZ industrial ni una segmentación IEC 62443 certificada.

## 5. Paso a paso

### Paso 0 — Restablecer y tomar la línea base

Ejecute la acción permitida `reset` desde la UI **Restablecer laboratorio** o, sin depender del navegador, dentro del contenedor fijo `plant`:

```bash
docker compose exec -T plant python -c 'import urllib.request; r=urllib.request.Request("http://127.0.0.1:8000/api/scenario/reset", method="POST"); print(urllib.request.urlopen(r).read().decode())'
```

Compruebe el estado del gemelo:

```bash
docker compose exec -T plant python -c 'import urllib.request; print(urllib.request.urlopen("http://127.0.0.1:8000/api/state").read().decode())'
```

La línea base esperada es `traffic_signal=2` (verde), `speed_setpoint=45` y `safety_trip=false`. Tome una captura de la vista 3D nominal. El `reset` es una operación de API: **no lo describa como una trama DNP3**.

### Paso 1 — Medida inicial por DNP3

El master nativo puede leer el punto de retorno sin ejecutar un control:

```bash
docker compose exec -T trainer python /lab/dnp3/native_master.py observe
```

Registre el JSON sin modificarlo. En línea base se espera `protocol=DNP3`, `operation=observe`, `analog_input_index=0` y `value=2`. Es una lectura puntual solicitada por el alumno o por la comprobación; no es una afirmación de que exista tráfico DNP3 periódico.

El `trainer` sí mantiene una línea base periódica de **Modbus FC03** cada aproximadamente tres segundos para otros ejercicios. Esa actividad es distinta de DNP3. No invente tráfico periódico OPC UA o DNP3: OPC UA se activa solo en su escenario específico y este laboratorio genera DNP3 al ejecutar `dnp3-signal`.

### Paso 2 — Control DNP3 permitido

Desde la consola pulse **Señal DNP3**, o ejecute el cliente fijo en `trainer`:

```bash
docker compose exec -T trainer python /lab/dnp3/native_master.py signal 0
```

El cliente implementado en `dnp3/native_master.py` hace lo siguiente:

- conecta exclusivamente a `plant:20000`;
- construye una trama DNP3/TCP con preámbulo `05 64`, cabecera de enlace y CRC DNP por bloques;
- emite una operación de salida analógica **Group 41 Variation 1**, índice 0, valor 0 (la práctica usa una operación directa en un solo segmento);
- valida la respuesta del outstation y el estado de la operación;
- ejecuta una lectura **Group 30 Variation 1**, índice 0, hasta observar el valor solicitado;
- imprime `status=VERIFIED_BY_DNP3_READBACK` cuando el retorno es 0.

El outstation aplica el cambio mediante una llamada interna al API del gemelo. Esa llamada explica el cambio de `traffic_signal`, pero no convierte el HTTP interno en la transacción DNP3. La transacción entre master y outstation sí es DNP3/TCP; la API interna es solo parte del emulador.

**Precisión:** `05 64` identifica el comienzo de una trama DNP3 en este flujo, pero no prueba por sí solo que se haya ejecutado un control, que el mensaje sea malicioso o que una señal haya cambiado. Hay que identificar dirección, stream, payload, respuesta, logs y estado/readback.

### Paso 3 — Observar la vista SCADA/3D y el estado

En la consola local deben observarse el semáforo **virtual** en rojo y el evento DNP3. Consulte también el estado de la API:

```bash
docker compose exec -T plant python -c 'import urllib.request; print(urllib.request.urlopen("http://127.0.0.1:8000/api/state").read().decode())'
```

Busque `traffic_signal: 0`. No suponga que un cartel, una alarma o cualquier otro componente cambió si no aparece en el estado o en el evento. La pantalla es una representación del gemelo; no es prueba de un actuador físico. El archivo `app/core.py` marca el efecto como **SIMULADO**.

Registre fuentes separadas:

1. salida del master (`VERIFIED_BY_DNP3_READBACK`);
2. PCAP DNP3;
3. `/api/state` y/o evento DNP3;
4. captura de pantalla antes/después.

La alerta heurística `OT-ANOMALY` o una firma EVE, si aparece, es analítica y no sustituye a la trama ni prueba intención adversaria.

### Paso 4 — Captura enfocada de DNP3

Para no mezclar otros ejercicios, haga una captura de 12 segundos en el contenedor `plant` y lance solo la acción DNP3 desde `trainer`. El volumen `./pcaps:/captures` deja el archivo en el anfitrión:

```bash
docker compose exec -T plant timeout 12 tcpdump -i any -U -s 0 -w /captures/04-dnp3.pcap 'tcp port 20000' >/dev/null 2>&1 &
CAP_PID=$!
sleep 2
docker compose exec -T trainer python /lab/dnp3/native_master.py signal 0
wait "$CAP_PID" || test "$?" -eq 124
sha256sum pcaps/04-dnp3.pcap
```

El archivo puede incluir handshake TCP, cierre y uno o más segmentos con payload. No edite el PCAP. Si necesita una captura de referencia que el repositorio ya ofrece, `bash scripts/baseline-capture.sh` es reproducible, pero lanza `modbus-write`, `opcua-write`, `dnp3-signal` e `intercept`; en ese caso, delimite en el informe qué parte es de DNP3 y qué parte pertenece a otros laboratorios. Ese script tampoco convierte FC03 en tráfico DNP3.

### Paso 5 — Inspección con tshark

Primero enumere la captura y filtre por el puerto fijo:

```bash
capinfos pcaps/04-dnp3.pcap
tshark -r pcaps/04-dnp3.pcap \
  -Y 'tcp.port == 20000' \
  -T fields \
  -e frame.number -e frame.time_relative -e ip.src -e ip.dst \
  -e tcp.stream -e tcp.len -e tcp.flags -e data.data
```

Para revisar la disección DNP3 cuando la versión de Wireshark la reconoce:

```bash
tshark -r pcaps/04-dnp3.pcap -Y 'dnp3' -V | sed -n '1,240p'
```

Si `dnp3` no es un filtro válido en la instalación, use `tcp.port == 20000` y la inspección hexadecimal; no invente campos de protocolo. Para localizar el preámbulo en payload TCP:

```bash
tshark -r pcaps/04-dnp3.pcap \
  -Y 'tcp.port == 20000 && tcp.len > 0' \
  -T fields -e frame.number -e tcp.stream -e data.data
```

O con `tcpdump`:

```bash
tcpdump -nn -r pcaps/04-dnp3.pcap 'tcp port 20000'
```

#### Qué buscar

- La conexión TCP al puerto 20000 y el `tcp.stream` correcto.
- Payload de master a outstation que comienza con `05 64` cuando el segmento contiene el inicio de una trama.
- Dirección de solicitud y dirección de respuesta; no llame “respuesta” al primer paquete que aparece.
- La operación de control y su respuesta, seguida de la lectura de retorno. La implementación del repositorio valida Group 41/Variation 1 para la respuesta de control y Group 30/Variation 1 para la lectura analógica.
- CRC DNP como detección de error de trama, no como firma criptográfica.
- Si hay reensamblado, segmentación o falta de disección, anótelo como límite; no reconstruya una trama no demostrada.

No atribuya a la captura el texto del navegador, el JSON de `/api/state`, el mensaje de toast o la alerta de Suricata. Esos datos pueden tener timestamp y origen propios. El PCAP contiene tráfico que realmente atravesó la interfaz capturada, no todo lo que la UI mostró.

### Paso 6 — Tabla de correlación y evidencias

Complete una fila por evento. No rellene horas o bytes inventados:

| Hora UTC | Origen | Función/objeto DNP3 | Valor solicitado | Valor observado | Señal virtual | Evidencia independiente |
|---|---|---|---:|---:|---|---|
| `<timestamp de la salida o evento>` | `trainer/master` | Direct Operate, AO Group 41 Var 1, índice 0 | `0` | `0` por Group 30 Var 1 | `traffic_signal=0`, rojo | `04-dnp3.pcap` + JSON `VERIFIED_BY_DNP3_READBACK` |
| `<timestamp de /api/state>` | `plant/gemelo` | No es una función DNP3; es estado de aplicación | — | `traffic_signal=0` | Rojo virtual | JSON de estado + captura SCADA/3D |

El valor “observado” del primer renglón debe venir de la lectura DNP3 del master, no solo de la pantalla. El valor del segundo renglón debe venir de la API o evento, no de una inferencia sobre bytes. Añada `sha256sum` del PCAP y la versión de las herramientas.

**Entregable mínimo:**

- PCAP DNP3 enfocado o extracto reproducible con filtro y hash;
- salida del master con readback;
- una captura de la vista nominal y otra roja;
- tabla de correlación;
- interpretación MITRE/IEC y límites/antipatrones.

## 6. Matriz MITRE ATT&CK for ICS

### Mapeo aplicado

| Evidencia de la maqueta | Técnica/táctica | Justificación y alcance | No demuestra |
|---|---|---|---|
| Orden DNP3 al AO índice 0, respuesta válida, readback 0 y cambio del gemelo | **T0831 — Manipulation of Control**, táctica **Impact** | MITRE describe manipulación del control de procesos, incluidos comandos/parámetros. Aquí la conducta se representa de modo autorizado y educativo: el master cambia una señal virtual fija. | No demuestra adversario, campaña, intrusión, intención, acceso no autorizado ni que un equipo real haya sido manipulado. |
| Una única orden y una única lectura de retorno | **No asignar T0806** | T0806 — Brute Force I/O trata cambios repetitivos o sucesivos de puntos. Este laboratorio no genera una secuencia repetida de cambios; no se inventa una relación. | No llamar “brute force” a la presencia de una sola escritura. |

La página oficial de T0831 indica además mitigaciones de autenticidad de comunicaciones y validación fuera de banda. En un diseño real se estudiarían autenticación de master/outstation, allowlists, autorización por rol, límites de punto, registro inmutable y una verificación independiente antes de reanudar control. **Este laboratorio no implementa DNP3 Secure Authentication.**

El panel puede mostrar una alerta analítica o Suricata puede escribir EVE JSON. Eso ayuda a enseñar detección, pero no es una “detección MITRE” automática ni reemplaza la evidencia de red. El propio material de ATT&CK debe consultarse en su versión vigente: las técnicas, versiones y procedimientos pueden cambiar.

## 7. Mapeo conceptual IEC 62443

IEC 62443 organiza requisitos técnicos en FR y relaciona requisitos, mejoras y niveles de seguridad con zonas y conductos. La siguiente matriz es **conceptual** para discutir diseño; no es una auditoría, un cálculo de SL, una certificación ni una declaración de conformidad.

| FR | Aplicación en este laboratorio | Control/medida que debería existir en un sistema real | Limitación actual |
|---|---|---|---|
| **FR2 — Use control** | Solo la acción predefinida `dnp3-signal` puede emitir la operación del ejercicio; el destino y el rango están cerrados. | Identidad fuerte, roles separados, mínimo privilegio, aprobación de escrituras, allowlist de puntos y horarios, registro de quién autorizó. | Token de demostración y botón local no son IAM de producción. |
| **FR3 — System integrity** | El master valida respuesta y readback; el PCAP permite comparar orden y respuesta. | Autenticidad criptográfica del canal, control de cambios, firmware/configuración protegidos, verificación de punto y recuperación conocida. | CRC DNP detecta errores, pero no proporciona autenticidad. El readback por sí solo no garantiza seguridad física. |
| **FR5 — Restricted data flow** | `control` es `internal: true`, no se publican 20000/502/4840 y el cliente usa `plant:20000`. | Zonas y conductos con firewall/allowlist, separación de niveles y rutas de administración, egress controlado, sensores pasivos autorizados. | El bridge de Docker no es una DMZ industrial y la agregación de roles no reproduce segmentación física. |
| **FR6 — Timely response to events** | Se correlacionan evento, PCAP, readback y estado para detectar y contener. | Monitorización con contexto, playbook, responsable, confirmación fuera de banda, retención de logs y pruebas de recuperación. | No hay SLA, equipo operativo ni respuesta de incidente real. |

No atribuya a IEC 62443 una certificación del repositorio. La meta de un taller es aprender a documentar brechas y controles, no declarar un Security Level.

## 9. Contención segura propuesta

Si esto fuera una señal no autorizada en un sistema real, una respuesta defensiva de alto nivel sería:

1. mantener la supervisión y la seguridad del proceso; no cortar indiscriminadamente las comunicaciones de control;
2. restringir temporalmente el origen autorizado del conducto de escritura mediante el cambio aprobado de allowlist/firewall;
3. preservar PCAP, logs del master/outstation, estado del punto y hora sincronizada;
4. revisar si la orden fue autorizada y si la respuesta/readback coincide;
5. validar el estado del punto con un canal o instrumento independiente antes de reabrir la vía;
6. escalar por el procedimiento de incidentes y documentar cada decisión.

En esta maqueta, la contención didáctica consiste en **no conectar activos reales**, conservar evidencia y ejecutar `reset` solo como cierre del escenario. No confunda el interlock de software del gemelo con un SIS certificado.

## 10. Antipatrones que invalidan el informe

- Publicar `20000/TCP` o cambiar `plant:20000` por una IP, DNS o equipo real.
- Ejecutar la práctica desde una red OT o probar contra una RTU/PLC de terceros.
- Describir la acción del navegador como si el navegador fuese el master DNP3.
- Usar el contenido del panel, `/api/state` o una alerta Suricata como si fueran bytes del PCAP.
- Concluir “hubo ataque” por `05 64`, por una escritura autorizada o por un nombre de técnica ATT&CK.
- Llamar DNP3 periódico a las lecturas FC03 Modbus de línea base, o inventar tráfico OPC/DNP que no se ejecutó.
- Llamar proxy transparente, MITM o ARP spoofing al proxy Modbus de otro ejercicio: ese proxy envía una trama editada al único destino fijo `plant:502`.
- Presentar la maqueta 3D como PLC, RTU, semáforo físico, SIS o hardware de seguridad.
- Presentar CRC como autenticación, o afirmar que existe DNP3 Secure Authentication.
- Reclamar certificación, Security Level o cumplimiento IEC 62443 a partir de esta guía.
- Citar T0806 u otro identificador sin la conducta y la fuente que lo justifican.

## 12. Límites declarados

- No hay hardware PLC, RTU físico, actuador, semáforo público ni SIS; todo el efecto es software/3D.
- No se implementa DNP3 Secure Authentication. El CRC no es autenticación criptográfica.
- El master y outstation cubren una transacción mínima: no representan una pila DNP3 general, fragmentación arbitraria, interoperabilidad industrial ni validación de producto.
- El proxy Modbus de otros laboratorios no es una intercepción transparente ni un MITM.
- PCAP, logs de aplicación, API, UI y Suricata son fuentes distintas y no contienen automáticamente la misma información.
- El `baseline-capture.sh` mezcla escenarios; la captura enfocada de esta guía es preferible para atribuir DNP3.
- El mapeo ATT&CK es de conducta representada, no una atribución. T0806 no se asigna porque no hay cambios repetidos de I/O.
- El mapeo IEC 62443 es conceptual y no implica certificación, SL ni conformidad.
- La Ley 21.663 es contexto general; no se derivan sujetos obligados, plazos, multas ni asesoría legal.
- Las únicas acciones de este laboratorio son `dnp3-signal` y `reset`, siempre hacia destinos fijos internos Docker.
El archivo puede incluir handshake TCP, cierre y uno o más segmentos con payload. No edite el PCAP. Para esta práctica no ejecute `baseline-capture.sh`, porque ese script lanza escenarios de otros laboratorios; solo consúltelo como referencia de que la línea base periódica es **Modbus FC03** y de que una captura multi-protocolo debe etiquetar su alcance. Ese script tampoco convierte FC03 en tráfico DNP3.
